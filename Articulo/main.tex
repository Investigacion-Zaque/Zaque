\begin{abstract}

La agricultura de precisión ha revolucionado la producción agrícola mediante la incorporación de tecnologías IoT. Sin embargo, gran parte de las soluciones disponibles dependen de conectividad permanente a Internet y servicios en la nube, limitando su implementación en zonas rurales donde la infraestructura de telecomunicaciones es insuficiente. Este artículo presenta ZAQUE, un sistema distribuido de monitoreo agrícola local diseñado específicamente para operar en entornos con conectividad limitada. La arquitectura propuesta integra una red de nodos ESP32, uno configurado como estación principal (MAIN) y múltiples nodos sensores (SENSOR), comunicados mediante WiFi local. Cada nodo incorpora sensores Modbus RS485 para medición multiparamétrica del suelo, módulos GPS para georreferenciación, y almacenamiento local en microSD para garantizar persistencia de datos. El nodo MAIN expone un dashboard web embebido accesible desde dispositivos móviles sin requerir acceso a Internet. El sistema incluye un motor de recomendaciones agrícolas basado en reglas que genera alertas útiles en lenguaje natural para el campesino. Los resultados demuestran la viabilidad de una solución de bajo costo (~USD 100 por nodo) capaz de apoyar agricultura de precisión en comunidades rurales con conectividad limitada.

\end{abstract}

\section{Introducción}

La agricultura moderna enfrenta desafíos crecientes: aumento de población global, limitaciones de agua dulce, degradación de suelos y presión por mejorar rendimientos. En este contexto, la agricultura de precisión emerge como estrategia tecnológica fundamental que permite monitorear variables ambientales a nivel microlocal para optimizar recursos naturales.

El Internet de las Cosas (IoT) ha democratizado el acceso a sensores de bajo costo capaces de recopilar datos ambientales. Sin embargo, la mayoría de soluciones IoT comerciales (Agritech, Plantwise, Arable) dependen de plataformas en la nube, requiriendo conectividad permanente a Internet. En Colombia, según el Ministerio de TIC, aproximadamente 30\% de la población rural carece de acceso a conectividad confiable, limitando la adopción de estas tecnologías.

ZAQUE surge como respuesta a esta brecha: un sistema de monitoreo agrícola que funciona completamente offline en redes WiFi locales, permitiendo que un campesino use la zona móvil de su celular para conectar múltiples sensores distribuidos en su finca y visualizar toda la información desde un navegador web en su dispositivo móvil.

\section{Arquitectura del Sistema}

\subsection{Visión General}

ZAQUE implementa una arquitectura distribuida multinodo con dos roles diferenciados ejecutados en hardware idéntico (ESP32):

\begin{itemize}
\item \textbf{Nodo MAIN}: Estación central que actúa como servidor web, procesador de datos y almacenamiento principal. Ejecuta permanentemente un servidor HTTP local accesible en \texttt{http://zaque.local}.
\item \textbf{Nodos SENSOR}: Dispositivos distribuidos en el terreno agrícola que ejecutan ciclos de medición periódica, envían datos al MAIN mediante HTTP POST, y entran en deep sleep para conservar energía.
\end{itemize}

La comunicación entre nodos ocurre a través de una red WiFi local, típicamente la zona móvil del celular del campesino (hotspot), eliminando la dependencia de infraestructura externa.

\subsection{Componentes Principales}

\subsubsection{Nodo MAIN}

El nodo MAIN implementa las siguientes responsabilidades:

\begin{enumerate}
\item \textbf{Adquisición de datos}: Lectura local de sensores Modbus RS485, GPS, y batería.
\item \textbf{Servidor web embebido}: Hosting de un dashboard HTML/CSS/JS directamente en el ESP32.
\item \textbf{API REST local}: Endpoints HTTP para recibir mediciones de nodos SENSOR.
\item \textbf{Almacenamiento persistente}: Registro de mediciones en microSD en formato CSV y JSON.
\item \textbf{Procesamiento de recomendaciones}: Análisis de variables agrícolas y generación de alertas.
\item \textbf{Registro de nodos}: Mantenimiento de estado de todos los sensores conectados.
\end{enumerate}

\subsubsection{Nodos SENSOR}

Los nodos SENSOR ejecutan un ciclo repetitivo de bajo consumo:

\begin{enumerate}
\item \textbf{Despertar periódico}: Por defecto cada 30 minutos.
\item \textbf{Lectura de sensores}: Adquisición de mediciones Modbus en ~5 segundos.
\item \textbf{Lectura GPS}: Obtención de coordenadas o ubicación por defecto.
\item \textbf{Envío HTTP}: Transmisión de medición al MAIN en ~2 segundos.
\item \textbf{Deep sleep}: Entrada a modo de bajo consumo (~0.5 mA).
\end{enumerate}

Este ciclo permite autonomía de 1-3 meses con batería estándar de 2000 mAh.

\subsection{Microcontrolador}

Se utiliza la plataforma ESP32 DevKit debido a:

\begin{itemize}
\item WiFi 802.11b/g/n integrado
\item Arquitectura dual-core a 240 MHz
\item 4 MB Flash + 520 KB RAM
\item 36 GPIO configurables
\item Soporte nativo para deep sleep y RTC
\item Costo accesible (~USD 15)

Las mediciones se almacenan en microSD en dos formatos:

\subsubsection{Formato CSV}

Archivo \texttt{/measurements.csv} con estructura de tabla para análisis histórico:

Archivo \texttt{/latest.json} con última medición de cada nodo para dashboard:

\begin{lstlisting}

\section{Motor de Recomendaciones Agrícolas}

\subsection{Arquitectura del Motor}

El sistema implementa un motor de recomendaciones basado en reglas (rule-based) que analiza mediciones y genera alertas en lenguaje natural útiles para el campesino.

El motor sigue una jerarquía de prioridades:

\begin{enumerate}
\item \textbf{Validación}: Verifica que la medición contiene datos suficientes.
\item \textbf{Alertas críticas}: Identifica condiciones peligrosas inmediatas.
\item \textbf{Combinaciones críticas}: Analiza interacciones entre variables.
\item \textbf{Variables individuales}: Evalúa cada parámetro en rango normal.
\item \textbf{Estado óptimo}: Confirma cuando todo está bien.
\end{enumerate}

\subsection{Reglas Implementadas}

\subsubsection{Alertas Críticas}

\begin{table}[h]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Condición} & \textbf{Alerta} \\
\hline
Humedad < 25\% & Estrés hídrico severo \\
\hline
Humedad > 85\% & Riesgo de encharcamiento \\
\hline
CE > 4.0 mS/cm & Exceso de sales \\
\hline
\end{tabular}
\end{table}

\subsubsection{Combinaciones Críticas}

\begin{table}[h]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Combinación} & \textbf{Recomendación} \\
\hline
Humedad < 40\% AND T > 28°C & Estrés hídrico + calor \\
\hline
pH < 5.5 AND P < 15 mg/kg & Bloqueo nutricional \\
\hline
Humedad > 70\% AND CE > 2.0 & Acumulación de sales \\
\hline
pH > 7.5 AND (N/P/K bajo) & Bloqueo por alcalinidad \\
\hline
\end{tabular}
\end{table}

\subsubsection{Recomendaciones Individuales}

Para cada variable, el motor genera texto adaptado:

\begin{itemize}
\item \textbf{Humedad}: Incluye valor actual y recomendación de riego.
\item \textbf{pH}: Describe acidez/alcalinidad y sugiere correcciones.
\item \textbf{NPK}: Valora deficiencias y recomienda fertilización.
\item \textbf{CE}: Alerta sobre salinidad acumulada.
\item \textbf{Temperatura}: Advierte sobre estrés térmico.
\end{itemize}

\subsection{Ejemplo de Generación de Alerta}

Medición:
\begin{verbatim}
humidity: 35%, temperature: 28°C, pH: 6.2, N: 25
\end{verbatim}

Análisis:
- Humedad < 40\% ✓
- Temperatura > 28°C ✓
- Combinación presente

Alerta generada:
\begin{verbatim}
"🟠 ESTRÉS HÍDRICO: Humedad 35% + temperatura 28°C 
 alta. Revise riego urgentemente."
\end{verbatim}

\section{Estructura del Firmware}

\subsection{Modularización}

El firmware zaque\_device.ino se divide en componentes con interfaces bien definidas:

\begin{enumerate}
\item \textbf{config.h}: Configuración centralizada (roles, pines, WiFi, valores por defecto).
\item \textbf{types.h}: Estructuras de datos (\texttt{Measurement}) e interfaces virtuales.
\item \textbf{sensor\_reader.cpp}: Lectura del sensor Modbus RS485.
\item \textbf{gps\_reader.cpp}: Lectura GPS con fallback automático.
\item \textbf{sd\_logger.cpp}: Almacenamiento en microSD.
\item \textbf{wifi\_manager.cpp}: Gestión de conexión WiFi.
\item \textbf{http\_client.cpp}: Cliente HTTP para nodos SENSOR.
\item \textbf{web\_server.cpp}: Servidor web para nodo MAIN.
\item \textbf{node\_registry.cpp}: Registro de nodos (MAIN).
\item \textbf{recommendations.cpp}: Motor de recomendaciones.
\item \textbf{dashboard\_html.h}: HTML/CSS/JS embebido.
\end{enumerate}

\subsection{Compilación Condicional por Rol}

En \texttt{config.h}:

\begin{lstlisting}
#define DEVICE_ROLE DEVICE_ROLE_MAIN    // o DEVICE_ROLE_SENSOR
\end{lstlisting}

El compilador incluye/excluye código según el rol:

\begin{lstlisting}
#if DEVICE_ROLE == DEVICE_ROLE_MAIN
  // Código solo para MAIN
#endif
\end{lstlisting}

Esto permite compartir 90\% del código entre ambos roles.

\section{Manejo de Errores y Resiliencia}

\subsection{GPS Fallback}

Si el GPS no obtiene señal después de 1 segundo, el sistema automáticamente usa la ubicación por defecto definida en config.h:

\begin{lstlisting}
#define DEFAULT_LATITUDE 4.663198720911477f
#define DEFAULT_LONGITUDE -74.05499259771824f
\end{lstlisting}

Este mecanismo garantiza que las mediciones nunca se pierden por falta de GPS.

\subsection{SD Logger Robusto}

El logger de SD implementa validaciones:

\begin{enumerate}
\item Verifica que la tarjeta está correctamente inicializada.
\item Crea archivos con encabezados CSV solo en primera escritura.
\item Valida serialización JSON con verificación de bytes escritos.
\item Registra errores en serial para debugging.
\end{enumerate}

\subsection{Reintentos HTTP}

Los nodos SENSOR implementan reintentos con backoff exponencial:

\begin{lstlisting}
sendWithRetry(measurement, max_retries=3)
\end{lstlisting}

Si el MAIN no responde, la medición se almacena localmente para envío posterior.

\section{Consumo Energético}

\subsection{Nodo SENSOR}

\begin{table}[h]
\centering
\begin{tabular}{|c|c|c|}
\hline
\textbf{Estado} & \textbf{Consumo} & \textbf{Duración} \\
\hline
Despertar + Inicialización & 150 mA & 3 seg \\
\hline
Lectura de sensor & 80 mA & 2 seg \\
\hline
Lectura GPS & 100 mA & 1 seg \\
\hline
Envío HTTP & 120 mA & 2 seg \\
\hline
Deep sleep & 0.5 mA & 30 min - 8 seg \\
\hline
\end{tabular}
\end{table}

Consumo promedio por ciclo (30 min):
\begin{itemize}
\item Ciclo activo: ~70 mA durante 8 segundos
\item Ciclo dormido: ~0.5 mA durante 29 min 52 seg
\item Promedio: $\frac{70 \times 8 + 0.5 \times 1792}{1800} \approx 0.35$ mA
\end{itemize}

Con batería de 2000 mAh: $\frac{2000}{0.35} \approx 5700$ horas $\approx 237$ días $\approx$ 7.8 meses.

\subsection{Nodo MAIN}

\begin{itemize}
\item WiFi siempre activo: ~80 mA
\item Servidor web activo: ~50 mA
\item Lectura de sensores periódica: ~20 mA promedio
\item Consumo total: ~150 mA promedio
\end{itemize}

El nodo MAIN debe estar conectado a alimentación permanente (AC, solar, o batería grande con carga).

\section{Seguridad}

\subsection{MVP (Actual)}

\begin{itemize}
\item \textbf{API Key}: Simple header hardcodeado en config.h.
\item \textbf{Red}: WiFi local no requiere HTTPS.
\item \textbf{Validación}: Verificación JSON básica de campos requeridos.
\item \textbf{Autenticación}: Ninguna (red local confiable).
\end{itemize}

\subsection{Recomendaciones Futuras}

\item Añadir HTTPS cuando haya conectividad a Internet.
\item Encriptación de datos sensibles en microSD.
\item Control de acceso por rol en dashboard web.
\item Logging de auditoría de operaciones críticas.
\end{enumerate}

\section{Ventajas de la Solución}

\begin{enumerate}
\item \textbf{Operación sin Internet}: Funciona completamente offline en red WiFi local.
\item \textbf{Bajo costo}: ~USD 100 por nodo completo.
\item \textbf{Escalabilidad}: Soporte teórico ilimitado de nodos, limitado por rango WiFi.
\item \textbf{Almacenamiento seguro}: Datos persisten localmente en microSD.
\item \textbf{Facilidad de despliegue}: Hardware y software listos para usar.
\item \textbf{Independencia tecnológica}: No depende de proveedores de servicios en la nube.
\item \textbf{Inteligencia local}: Recomendaciones generadas en el dispositivo.
\item \textbf{Bajo consumo}: Autonomía de 1-3 meses para nodos SENSOR.
\end{enumerate}

\section{Limitaciones Actuales}

\begin{enumerate}
\item \textbf{Rango WiFi}: Limitado a ~50-100 metros dependiendo de interferencias.
\item \textbf{Sincronización}: No hay sincronización de estado entre nodos (cada uno es independiente).
\item \textbf{Descubrimiento}: El MAIN debe tener dirección fija o mDNS funcionando.
\item \textbf{Dashboard}: Versión actual es básica (mejoras futuras).
\item \textbf{Análisis}: Recomendaciones son reglas simples (sin ML/AI aún).
\end{enumerate}

\section{Conclusiones}

ZAQUE demuestra la viabilidad de un sistema de monitoreo agrícola local, distribuido y de bajo costo para comunidades rurales con conectividad limitada. La arquitectura basada en ESP32 permite capturar variables críticas del suelo (humedad, pH, NPK), almacenarlas localmente, y proporcionar recomendaciones agrícolas inteligentes sin depender de infraestructura externa.

Las principales contribuciones de este trabajo son:

\begin{enumerate}
\item Arquitectura modular y escalable ejecutable en hardware de ~USD 100.
\item Motor de recomendaciones basado en reglas agrícolas validadas.
\item Mecanismos de resiliencia (GPS fallback, reintentos HTTP, SD redundante).
\item Consumo energético optimizado para autonomía extendida.
\item Documentación completa y código de software libre.
\end{enumerate}

Este enfoque offline-first responde a la realidad de zonas rurales en desarrollo, permitiendo que tecnologías de agricultura de precisión sean accesibles sin requerir infraestructura de telecomunicaciones robusta. Se espera que ZAQUE sea una herramienta útil para pequeños y medianos agricultores, extensionistas rurales, y investigadores agrícolas en entornos con limitaciones de conectividad.
